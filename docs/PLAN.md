## 2. قرارات الخطة (الخيارات والموصى به)

| القرار | الخيارات | التوصية |
|---|---|---|
| طريقة البناء | (أ) طبقة طبقة: القاعدة كلها ثم الخلفية ثم الواجهة · (ب) **شرائح رأسية**: كل مرحلة وحدة وظيفية كاملة (قاعدة + API + واجهة + اختبارات) | **(ب)** — شيء يعمل ويُجرَّب في كل مرحلة، وأخطاء التصميم تظهر مبكراً |
| ترتيب الوحدات | (أ) حسب التبعيات الفنية · (ب) حسب أولوية الأعمال أولاً | **(أ) مع أولوية للمخاطر العالية**: الأساس ← الموظفون ← الموافقات ← الإجازات ← الحضور ← الرواتب (تعتمد على ما قبلها) |
| الوثائق الصادرة (letters) | قبل الرواتب / بعدها / بالتوازي | **قبل الرواتب** — قيمتها سريعة لـ HR، ومخاطرها منخفضة، وتختبر حاوية `render` مبكراً على ARM64 |
| الجداول المهاجَرة | كل جداول الوحدة دفعة واحدة / عند الحاجة | **عند الحاجة**: كل مرحلة تُنشئ جداولها فقط (تهجيرات SQL صغيرة متتابعة) |
| بيانات الاختبار | يدوية / بذور (seed) مولَّدة | **بذور مولَّدة** (شركة، فروع، 200 موظف، سنة حضور) لتجربة الأداء والتقارير مبكراً |
| الإصدار الأول | كل الوحدات دفعة واحدة / تدريجي | **تدريجي على Staging** بعد كل مرحلة، و**إنتاج واحد بعد المرحلة 9**، وبإمكان HR تجربة النواة قبل ذلك |
| تعريف «اكتملت المرحلة» | حسب التقدير / معيار ثابت | **معيار ثابت (DoD)** أدناه |

### تعريف الإنجاز (DoD) لكل مرحلة
- كل الشرائح الوظيفية تعمل من الواجهة إلى القاعدة، بالصلاحيات والنطاق والتدقيق.
- اختبارات الوحدات للمنطق، واختبارات التكامل على PostgreSQL حقيقي، وPlaywright للمسار الحرج.
- التهجيرات تعمل على قاعدة فارغة وعلى نسخة ببيانات، دون كسر الوحدات السابقة.
- OpenAPI محدَّث، والترجمة (عربي/إنجليزي) كاملة، وRTL سليم.
- CI أخضر (أنواع، lint، اختبارات، فحص ثغرات)، والنشر على Staging ناجح.
- تحديث هذه الوثيقة (الحالة والملاحظات) و`DESIGN.md` إن تغيّر تصميم.
